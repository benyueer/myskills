# AI Agent 简历撰写指南

## Overview

本技能帮助求职者撰写 AI Agent / LLM 应用 / RAG / 智能客服岗位的技术简历。适用于第一次写技术简历或第一次把 Agent 项目写进简历的求职者。内容包含 STAR 法则压缩、数字量化、技术栈展示、项目经历模板（Python/Java/Go）、各模块描述示例、常见问题诊断和投递前自检。

## When to Use

- 用户需要撰写 AI Agent 相关岗位的简历
- 用户需要优化现有 Agent 项目经历的描述
- 用户需要技术栈展示的参考写法
- 用户需要诊断简历中的常见问题
- 用户需要项目成果的量化方法指导

## 1. 简历撰写总原则

### STAR 法则在简历中的应用

| STAR 要素 | 简历里怎么写 | 劣质写法 |
|-----------|--------------|----------|
| S (情境) | 半句到一句：场景 + 规模（用户/请求量/文档量） | 「做了一个系统」 |
| T (任务) | 嵌入动词：为降低/为提升/为满足 SLA | 「负责开发」 |
| A (行动) | 关键技术名 + 你的动作（设计/实现/推动/排障） | 「使用各种技术」 |
| R (结果) | **数字**或**前后对比** | 「效果很好」「显著提升」 |

**万能句式（可直接套用）：**

> 在 **[场景与规模]** 下，为 **[目标指标]**，采用 **[方案 A + 关键技术名]**，**[你本人主导的动作]**，最终实现 **[量化结果 / 明确对比]**。

**范例对比：**
- **差：** 负责 RAG 模块，使用了向量数据库。
- **好：** 在日均 **1 万+** 问答请求的内部知识库场景下，为降低幻觉与尾延迟，采用 **混合检索（向量 + BM25）+ Cross-Encoder 重排**，并落地 **Redis 热点缓存** 与 **批量向量化** 配置，将 **P95 端到端延迟从 800ms 降至 320ms**，人工抽检 **回答准确率从 72% 提升至 86%**。

### 数字量化的重要性

| 类别 | 可写内容 |
|------|----------|
| **性能** | QPS、RPS、P95/P99 延迟、首字延迟（TTFT）、单次请求成本 |
| **质量** | 准确率、召回率、F1、MRR、nDCG、用户评分、bad case 占比 |
| **规模** | 文档条数、向量维度、索引分片、日活、会话轮次 |
| **效率与成本** | Token 消耗下降 %、GPU 占用、人力节省、迭代周期缩短 |
| **稳定性** | 可用性 99.X%、错误率、熔断次数、事故复盘后的改进 |

**若暂时没有线上指标**，可以诚实写：
- 「在自建 **200 条** 问答集上，F1 从 **0.61 → 0.79**」
- 「压测单机 **X req/s** 时 P95 **Y ms**」

### 技术深度 > 广度

- **浅：** 熟悉 RAG 与 Agent 开发。
- **深：** 针对多跳问答中「检索漂移」问题，对比 **仅向量检索** 与 **HyDE + 混合检索**，在业务测试集上选择后者，Recall@5 从 **0.58 提升至 0.81**，并记录失败样本用于周度迭代。

### 常见错误

| 错误类型 | 说明 | 改进方向 |
|----------|------|----------|
| 泛泛动词 | 「参与」「协助」「熟悉」无下文 | 改为「设计并实现」「将 X 从 A 优化到 B」 |
| 只堆名词 | 只写技术栈，不写动作 | 每个技术栈词后面跟「用来解决了什么问题」 |
| 抢功 | 把团队成果全写成「我」 | 写清「在 X 人团队中负责 Y 子系统」 |
| 无关堆砌 | 大段传统 CRUD，与 Agent 无关 | Agent 岗优先：编排、工具、RAG、评测、成本、延迟 |
| 泄密 | 写真实客户名、未公开数据 | 用「某金融客户」「Top3 互联网」 |

## 4. 各模块简历描述示例

### Agent 编排模块

1. 基于 **LangGraph / 自研有向图** 将业务拆成「意图识别 → 规划 → 工具调用 → 反思 → 最终回复」多节点流程，**状态持久化至 Redis/DB**，支持断点续跑与人工接管。
2. 配置 **最大步数、最大工具调用次数、重复调用检测**，将异常会话占比从 **X%** 降至 **Y%**。
3. 实现 **并行工具调用** 的结果合并与冲突消解，平均完成任务步数减少 **X 步**。
4. 对 **敏感操作** 设计 **确认节点与二次校验**，满足业务风控要求。

### RAG 检索模块

1. 搭建 **解析 → 清洗 → 分块 → 向量化 → 索引** 全链路，支持 **PDF/Word/HTML/表格** 等格式，全量索引 **X 万篇**、增量更新延迟 **< X 分钟**。
2. 采用 **稠密向量检索 + BM25（Elasticsearch）混合召回**，并用 **Cross-Encoder 重排**，Recall@5 从 **X** 提升至 **Y**。
3. 针对 **短问句、指代、多跳问题** 引入 **查询改写 / HyDE / 子查询分解**，「检索为空」类 bad case 下降 **X%**。

### 记忆系统

1. 设计 **会话级短期记忆（Redis）+ 用户级长期偏好（PostgreSQL）** 分层存储。
2. 采用 **摘要压缩 + 滑动窗口** 策略，平均 **每轮 token 消耗降低 X%**。
3. 对 **PII** 做脱敏与 **可删除设计**，满足合规要求。

### 工具系统

1. 基于 **OpenAPI / JSON Schema** 统一工具描述与入参校验。
2. 为工具调用增加 **鉴权、租户隔离、超时、重试与幂等键**，工具成功率从 **X%** 提升至 **Y%**。
3. 搭建 **工具调用全量日志与请求回放**，支撑 bad case 复现与提示词迭代。

### 模型路由与容错

1. 实现 **主备模型与多供应商路由**，按 **成本 / 延迟 / 能力** 配置策略，故障时 **自动切换**。
2. 对 **429、5xx、超时** 实施 **指数退避 + 熔断 + 舱壁隔离**，并结合 **热点问答缓存** 削减峰值依赖。
3. 建立 **按租户与按模型的成本仪表盘**，推动 **小模型兜底 + 大模型精修** 策略，月度成本下降 **X%**。

### 全链路追踪

1. 接入 **OpenTelemetry**，为请求生成 **Trace ID**，贯通 **网关、Agent、检索、工具、模型调用**。
2. 在 **LangSmith / Langfuse** 上关联单次对话与评测集条目，bad case 定位时间从 **X 分钟** 缩短至 **Y 分钟**。
3. 定义核心 **SLI（P95 延迟、错误率、工具失败率）** 与 **SLO**，接入告警与值班流程。

## 5. 中国简历「专业技能」结构（核心优势 + 技术栈）

中国技术简历常见的顶级结构是「专业技能」而非西方的 "Skills Summary"。推荐拆为两个子节：

### 核心优势（3～5 条，每条 2～3 行）

与「个人总结」的区别：
- 个人总结 = 自我评价（"5年经验、扎实基础"） → 太泛，面试官扫一眼就跳过
- 核心优势 = **领域能力标签 + 具体技术实践** → 面试官能直接从这里找到追问点

每条核心优势的写法公式：
> **[能力标签]**：[具体技术实践关键词1]、[关键词2]、[关键词3]，[你做了什么/能做什么]

AI Agent 岗位推荐的 5 大能力标签（按优先级排序）：
1. **Agent 系统架构与工程化落地** — Prompt 工程、上下文工程、RAG 全链路、工具调用、多 Agent 编排、状态持久化、评测回归
2. **Harness Engineering 实践能力** — 执行环境封装、工具注册与权限边界、结构化输出校验、失败重试与断点续跑、人机协作、全链路审计
3. **大模型与知识增强能力** — Agentic RAG、混合检索、重排、知识图谱增强、动态知识库、幻觉控制、复杂任务分解
4. **复杂系统架构与性能优化** — API/Worker 分离、BFF 架构、分布式任务编排、性能瓶颈优化
5. **云原生与平台化交付** — K8s、Helm、CI/CD、可观测平台、GPU 推理服务编排

**注意：** 核心优势必须基于真实经历，不要照抄模板中的夸大表述（如"PB 级数据治理""800 亿行实时计算"）。用自己项目的真实规模和技术实践替换。

**精准性原则：** 每条核心优势只放强关联内容，不要把不相关的技术塞进去。典型错误：把 Temporal（工作流引擎/基础设施层）写进 Harness Engineering（Agent 行为管控层）——两者有交集但不等同。Temporal 更适合放在「Agent 系统架构」或「后端与平台开发」中。

**术语标注法：** 对简历中出现的专业术语或非通用概念，在条目下方用可折叠块做两层说明：概念定义 + 项目实现。帮助非技术 HR 理解，同时给技术面试官提供追问锚点。

Jekyll 博客中使用 `<details>` + `<summary>` 实现可折叠：

```html
<details>
<summary>术语名称</summary>

概念定义：一句话说明是什么、解决什么问题。

**项目实现（项目名）**：在具体项目中怎么做的，用了什么技术、达到什么效果。

</details>
```

示例：

```html
<details>
<summary>LLM 网关全链路审计与溯源</summary>

对每一次 LLM 调用记录完整的请求-响应链路（输入 prompt、模型输出、耗时、token 用量、重试次数、成功/失败状态），持久化为可查询的审计日志，支撑 bad case 复现、prompt 版本回溯、成本分析与异常告警。

**实现方式**：基于 LiteLLM Proxy 构建统一模型网关，对接多厂商 LLM API（路由、流式 SSE、fallback 重试、超时控制）；集成 Langfuse 实现全链路可观测——自动 trace 每次调用的输入/输出/耗时/token 用量，支持 Prompt 版本管理、成本追踪、bad case 标注与效果回归。

</details>
```

**注意：** 术语标注应放在对应核心优势条目之后，而不是集中放在一起。每个术语折叠块紧跟其所属的能力标签条目。

### 技术栈（按分组 + 分级标注）

将技术栈按 5～6 个大类分组（如 AI Agent/大模型工程、模型与推理服务、后端与平台开发、大数据与数据治理、云原生与 DevOps、前端开发），每类内用分级标注区分深度：

- **熟练掌握** — 生产级落地经验，能独立设计与实现
- **熟悉** — 有项目实践经验，能在指导下完成
- **理解** — 有理论认知，能在团队协作中参与

分级标注比平铺式罗列更有层次，面试官能快速判断你的能力边界。注意：只写你真正做过的技术，不要为了凑数把没用过的框架写成「熟悉」。

## 6. 技能清单写法

```text
编程语言：Python（主力）、SQL、Shell
Agent 与 LLM：LangChain、LangGraph、提示词工程、工具调用（OpenAPI/JSON Schema）、简单评测与 bad case 分析
检索与 RAG：Milvus、Elasticsearch、混合检索、重排序、Embedding 模型选型与切块实验
后端：FastAPI、异步 IO、REST/SSE、鉴权与多租户（按实写）
数据：PostgreSQL、Redis、缓存与一致性经验（按实写）
工程化：Docker、CI/CD、单元测试/集成测试、基础 K8s
```

**排序技巧：**
1. JD 出现的关键词往前放
2. 每一行 **2～5 个具体词** 即可
3. 少用「熟悉/了解」；若用，必须跟具体事实
4. 不要单列「ChatGPT」；可写「大模型 API 集成与流式对话」

## 6. 常见问题诊断

### 问题 1：描述太笼统
- **修改前：** 负责公司 AI 项目开发。
- **修改后：** 负责企业知识库问答子系统：基于 **FastAPI + Milvus** 实现混合检索与重排，覆盖 **X 个业务线**、**Y 万份**文档，日均 **Z 万次**查询。

### 问题 2：没有量化数据
- **修改前：** 显著降低了延迟。
- **修改后：** 将检索链路 **P95 延迟从 650ms 降至 280ms**。

### 问题 3：技术栈罗列
- **修改前：** 使用 Python、LangChain、向量数据库、Redis。
- **修改后：** 使用 **Python + LangChain** 搭建 Agent；向量检索采用 **Milvus HNSW** 索引，**Redis** 缓存热点 query 的检索结果，命中后延迟 **< 50ms**。

### 问题 4：项目描述像说明文档
- **修改前：** 本系统是一个基于大模型的智能问答系统，用户在前台输入问题，系统调用后端，后端检索知识库并返回答案。
- **修改后：** 面向一线客服场景，打通 **多轮对话与工单检索**；本人负责 **检索与重排**，通过 **混合检索 + Cross-Encoder** 将 **Top-1 准确率从 52% 提升至 71%**。

## 7. 不同背景建议

### 应届生 / 小白
- 项目数量：**1～2 个**深挖远好于 **5 个**浅尝
- 没有线上数据：明确写「自建 N 条评测集」「离线 F1 / Recall@k」
- 避免：空泛「热爱 AI」、罗列网课、虚构大厂实习

### 1～3 年经验
- 每条经历写清：**你负责的模块**、**与谁协作**、**上线后的指标**
- 主动写 **1 条** 与 **事故、评测、成本、延迟** 相关的内容

### 转行人员
- 过去工作翻译成新语境：后端 → 稳定性、性能、接口契约
- 写清投入：「6 个月系统学习 + 2 个完整项目」

## 8. 投递前三问自检

1. **这条经历能否在面试里展开讲满 8～10 分钟？**（背景、方案、取舍、数据、复盘）
2. **简历上的数字是否经得起追问？**（口径、采样时间、环境）
3. **关键词是否与目标 JD 对齐？**（可适当同义替换，但不要造假经历）

好简历 = **真实经历 + 清晰结构 + 可验证结果**。

## Common Pitfalls

1. 使用「参与」「协助」等泛泛动词，没有具体动作和结果
2. 只堆技术名词，不说明解决了什么问题
3. 把团队成果全写成「我」，面试时无法自洽
4. 虚构业务数据，面试追问时说不清
5. 项目描述写成系统说明文档，而非个人贡献
6. 技能清单一行写 20 个词，没有分组和重点
7. 没有量化数据，面试官默认「没做过」
8. 把不相关的技术塞进同一条核心优势（如把 Temporal 写进 Harness Engineering），面试追问时暴露理解偏差
9. 技术栈写了一堆没用过的框架充数，面试一问就穿帮
10. 简历中提及第三方 AI 平台（Dify、RAGFlow、KnowDoc 等），容易让面试官质疑「是调了平台还是自己做的」——应统一表述为自研方案
11. 写了自研网关/审计系统但实际用的是 LiteLLM + Langfuse，面试追问实现细节时答不上来——如实写你用的工具，工具本身也是能力

## Verification Checklist

- [ ] 每条经历都包含 STAR 要素（场景、目标、行动、结果）
- [ ] 至少有 3 个可量化的数字指标
- [ ] 技术栈按分组展示，与 JD 关键词对齐
- [ ] 项目描述聚焦个人贡献，非系统介绍
- [ ] 没有泛泛动词（参与、协助、熟悉）
- [ ] 数字经得起追问（有口径、采样说明）
- [ ] 整体篇幅适合 10 秒扫读
